# 验收标准的可测性标注约定

> 起源：issue #37（2026-10-28）。#34 的验收写「artifact 可直接运行」，云端在**构建机本机**（Ubuntu 24.04）验证通过并记录——而文档示例指向 `debian:bookworm-slim`（GLIBC 2.36），目标环境照抄必失败（#35 的 `GLIBC_2.38 not found`）。**「在本机能跑」与「按文档在目标环境能跑」是两个命题，前者不断言后者。** #22（Windows 无 CI job）/ #28（Windows 测试 50% 失败）/ #26（地图无浏览器级测试）/ #35 四例同源：CI 验证代码，但不验证「交付形态」。本约定让每条验收标准**显式声明自己的验证方式**，使「绿了但跑不起来」的缺口在写验收时就被看见。

## 1. 三个标注

新 issue 的验收标准逐条标注（写在条目开头）：

| 标注 | 含义 | 纪律 |
| --- | --- | --- |
| `[CI]` | 有自动化验证，CI 会跑 | 必须指出**是哪个 job 的哪一步**（既有步骤或本 issue 新增步骤）；新增的写清失败形态 |
| `[手动+环境]` | 需人工验证 | **必须写明目标环境**（如「Windows + Docker Desktop」「真实 157 列塔类详单」）——验证者不许在自己的舒适环境里替代目标环境 |
| `[不可测]` | 主观判断 | 必须给出**判断依据**（判断者、对照材料）；「不可测」不是免检标签 |

## 2. 两条硬规则

1. **[手动+环境] 不写环境 = 验收不完整**——回退到验证者本机环境验证即复现 #34 的假阳性：构建机跑通、目标环境崩溃。
2. **文档示例默认 `[CI]`**：交付物（CI artifact、Release 资产）的官方消费示例，要么被 CI 实际构建运行（#37 的「文档即测试」——`scripts/extract-doc-dockerfile.py` 从文档提取 Dockerfile，duckdb job 末步实际 build+run，示例失效 CI 立即红），要么明确标注 `[手动+环境]` 并说明为何不进 CI。

## 3. 既有先例（本仓已落地的 [CI] 形态）

- **v0.20.4 前**：`TestAppVersionMatchesChangelogHead`（版本双锚定）、facts.md 全部机读计数门禁（工具数/路由数/迁移数）——「数字漂移即测试红」。
- **#37 落地**：duckdb CI job 的 `verify artifact runs in the documented base image` 步——从 `docs/fees-layer.md` §5.2 提取 Dockerfile（唯一事实源，提取器同时拒绝缺失 GLIBC 基线注），用刚产出的二进制实际构建、启动、断言 `/api/health` 与 DuckDB 引擎在位。文档改坏 → CI 红，不再等用户踩坑。
