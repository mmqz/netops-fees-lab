# 云网运维自动化：项目梗概

> 本文覆盖两个项目：**NetOps Lab**（云网资源治理与 AI 仿真工作台）与 **PCDN 自动化工具**（违规接入检测与封禁处置）。
> 两者的共同起点是同一个现实：**电信运营商的日常运维，大量时间耗在「从若干个网页系统里人工抄数据、人工判断、人工在另一个系统里操作」**。

---

## 一、一句话概括

| 项目 | 一句话 |
| --- | --- |
| **NetOps Lab** | 把分散在 Excel 台账里的 IPRAN 网络资源，变成一个**可查询、可校验、可仿真、AI 能直接读**的网络知识库，让「故障影响面分析」和「日常巡检」从人工查表变成一次查询。 |
| **PCDN 自动化工具** | 把「从 IDC 系统导流量报表 → 筛出异常账号 → 到 AIOBS 系统批量封禁」这条**每天重复的跨系统人工流水线**，做成可一键或定时执行的自动化链路。 |

两者都在解决同一个母问题：**运维工作被杂糅在多个互不相通的后台系统之间，人工搬运数据，既慢又不可追溯。**

---

## 二、解决了什么问题

### 2.1 共同的问题结构

```
   数据散落            判断靠人脑            操作在另一处
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│ Excel 台账    │   │ 经验 / 眼力   │   │ 后台系统点选  │
│ 多个网管系统   │──▶│ 逐条比对      │──▶│ 手工录入      │
│ 报表导出      │   │ 容易漏、难复现 │   │ 无留痕        │
└──────────────┘   └──────────────┘   └──────────────┘
      ↓                    ↓                    ↓
  格式不统一            判断不可审计         操作不可回滚
```

两个项目分别从两端切进去：

- **NetOps Lab** 解决左侧与中间——**把数据变成结构化的、可推理的模型**；
- **PCDN 工具** 解决中间与右侧——**把判断和操作串成一条端到端流水线**。

### 2.2 NetOps Lab 具体解决什么

**① Excel 台账进不来、进来了不可信**

运营商网管的资源数据通常导出成几十个 Excel：设备、板卡、端口、地址池、电路、基站、机房、局站、PTP 配置脚本……列名各家不同，一个文件几千行，靠肉眼核对。

- 解决方式：**列映射确认 → 行级记账 → 确定性校验**。
  每条导入行都有结果记账（成功 / 失败 / 跳过及原因），导入失败可追溯、可回滚；
  校验规则确定性可重算，同一份数据两次校验结果逐字节相同。
- 落地数据：**3,464 条资源、32 类资源、5,022 条关系、29 种关系类型**。

**② 网络资源之间「谁影响谁」说不清**

「这条光缆断了，影响多少基站、多少客户、多少业务？」——这个问题在纯 Excel 里几乎无法回答。

- 解决方式：**七层资源模型**（L0 空间 / L1 设备 / L2 光缆 / L3 传输 / L4 接入 / L5 逻辑 / L6 业务）加**显式关系图**。
  影响分析沿依赖方向做图上追溯，输出「受影响」与「候选根因」两类结果。
- **红线**：关系只来自数据显式声明，**绝不从名称、前缀、IP 段推断**——宁可答「不知道」，不可编造关系。

**③ 改动不敢做，因为改错了退不回来**

- 解决方式：**仿真工作台**。把导入资源一键物化成虚拟拓扑，在仿真态上做故障注入与状态变更，
  引擎给出确定性校验结果与前后对比，并提供**三层撤销**（事务回滚 / 变更集逆向 / 检查点）。
  **生产设备零写入**——这是写进仓库的合规红线。

**④ AI 拿不到结构化数据，只能在聊天框里猜**

- 解决方式：**MCP 工具面，11 个工具**——1 检索 + 4 仿真 + 5 只读分析 + 1 费用风险。
  AI 通过参数化只读查询拿真实数据，**永远不能传 SQL**。
- 附带能力：告警检测引擎（规则阈值 + 维护窗口抑制 + 根因/次生关联 + 抖动治理 + webhook 通知）、
  定时巡检调度器、质量报告、OpenAPI 自动生成文档（65 端点，与路由表零漂移）。

**⑤（v0.13 起）费用风险分析**

网络之外的第二条线：电费、铁塔租费、修理费、综维费。

- 解决方式：**SQLite 状态层 + Parquet 分区大表 + DuckDB 分析引擎**的分层架构。
  六大风险场景（退租后仍在计费 / 跨批次重复结算 / 合同账单金额差异 / 电费环比异常上涨 /
  同类站单位成本离群 / 零资源计费），输出**线索 + 阈值 + 行级证据锚点**。
- 关键纪律：**账单存在 ≠ 重复付款认定**。系统只给待核实线索，不做结论。

### 2.3 PCDN 工具具体解决什么

**① 每天要从两个内网系统之间人工搬数据**

```
IDC 流量监测系统 → 人工导出报表 → Excel 里筛选异常 → 整理名单 → AIOBS 批处置系统手工上传
       ↑                                                          ↑
  图形验证码（蓝色数学算式）                              有修改权限，点错就出事
```

这条链路原来每天人工做一遍：登录（含验证码）、导出 3–4 张报表、Excel 里筛、拼名单格式、上传封禁。

- 解决方式：**把整条链路自动化**——一键导出报表 → 自动筛选异常 → 自动生成 AIOBS 批处置名单 → 预检后上传 → 下载结果。

**② 图形验证码挡住了自动化**

系统验证码是**蓝色数学算式**（如 9-3=?），答案不在前端暴露。

- 解决方式：**专用验证码识别器**——蓝通道分割 + 腐蚀断开粘连 + 连通域分块 + 真实模板匹配 + 数学表达式规则纠错。
  实测真实样本 **10/10 全对**，同源测试 95% 文本正确率。
- 另有退路：**登录一次保存会话**（Token 与 Cookie 长期有效），日常 daemon 全自动、不碰验证码。

**③ 封禁操作危险，做错了影响真实用户**

- 解决方式：**预检 + 双重确认 + 处置工作台**。
  待处理池本地持久化（状态：待处理 / 处置中 / 已处置 / 失败待重试），可加备注（上门信息），
  上传失败自动回写池；可导出**上门名单**（账号|状态|备注）交给工程师现场处理。

**④ 还有「另一面」：解封**

违规封禁是业务的一面，另一面是「误封恢复」。第三方系统（端到端诊断 / 群障告警）没有解封按钮，
恢复权限通过**白名单**实现（群障告警白名单 / 光猫重启白名单）。相关接口已完成逆向分析并存档。

### 2.4 交付形态与社会成本

- **PCDN 工具**迭代了 v2.1.3 → v2.6.0 桌面版与 v3.0 Web 版，做了体积优化（467MB → 293.7MB，-37%）、
  修复打包缺陷、加了浏览器插件辅助、提供免 Python 环境的 exe 交付。
  **本质是把一个需要工程师现场鼓捣的脚本，做成办公台式双击就能用的工具**——交付对象是普通综维人员，不是程序员。
- **NetOps Lab** 走另一条路：单二进制 + 内嵌前端，一条命令起服务，CLI / HTTP / MCP 三出口，**本地优先、无外部依赖**。

| **运维面** | 写操作令牌门禁；整库在线备份；OpenAPI 自动文档；Windows 一键运行脚本 |

## 四、两个项目的技术取向对比

| 维度 | NetOps Lab | PCDN 工具 |
| --- | --- | --- |
| **面对的系统** | 自己建的（SQLite 本地库） | 别人的（内网 IDC / AIOBS / 诊断系统） |
| **技术路线** | Go 单二进制 + React + SQLite + DuckDB | Python + PyInstaller + OCR |
| **核心难点** | 数据建模、确定性、可追溯、AI 可读 | 逆向接口、验证码、跨系统串联、交付易用性 |
| **数据方向** | 只读 + 仿真（**零生产写入**） | **有写权限**（封禁/白名单）→ 因此要预检 + 确认 |
| **合规姿态** | 明确红线：不推断关系、不碰生产设备 | 明确边界：预检、小批量试、留痕 |
| **交付对象** | 开发 / 架构 /（远期）运营 | 一线综维人员（双击即用） |

**这两个项目其实是同一套问题意识的两种解题姿势**：
一个用工程化的方式重建数据底座，一个用逆向 + 自动化的方式接管既有系统的重复劳动。

## 五、共同的方法论沉淀

1. **确定性优先**：同一输入必须产出同一结果（时间戳来自数据而非服务器时钟；两次检测回执逐字节相同）。
2. **账本意识**：每一次导入、每一次检测、每一次处置都留**行级 / 批次级回执**，失败也留痕。
3. **可撤销**：改动必须能退（三层撤销 / 待处理池回写 / 会话可重建）。
4. **红线显式化**：什么能做什么不能做，写进文档而不是留在脑子里（零生产写入、关系不推断、账单存在≠认定结论）。
5. **降级要诚实**：能力不具备时给明确错误并附解法，绝不静默返回空数据。
6. **给机器留接口**：MCP / CLI JSON / OpenAPI，让 AI 和人用同一套事实。

## 六、适用范围与边界（如实说明）

**NetOps Lab**

- 面向 **IPRAN / 传输网**的资源治理与影响分析，数据源是网管导出的 Excel 台账；
- 演示数据来自互联网公开数据（OSM 局站/道路、OpenCelliD 基站）+ 模拟派生，**非运营商真实数据**；
- 当前**不具备生产设备写能力**，仿真仅限本地工作台；
- 费用分析层需要 DuckDB 构建（Windows 原生暂不可用，需走 Docker/WSL2）。

**PCDN 工具**

- 强依赖特定的三个内网系统（IDC 流量监测 / AIOBS 批处置 / 端到端诊断群障告警）与其接口形态；
- 需要云脉 VPN 才能访问内网；
- 验证码识别依赖模板库，样本积累越多越准；
- 封禁是**有真实影响的操作**，必须有预检和人工确认。

## 七、一句话收尾

> **这两个项目做的事，本质是把运维人员从「系统之间的搬运工」变回「判断者」——
> 让机器去跑那些重复的、格式化的、容易漏的环节，把需要经验与责任的部分留给人。**
