# [设计缺失] 告警与检测规则未纳入设计

关联：`docs/design/data-model-v1.md` §10.5、ADR-0011 D2/D3

## 问题

§10.5 的根因追溯写「步骤 4：与告警/性能数据交叉」，
但设计文档**只设计了性能（时序）存储，没有告警表与检测规则表**。

ADR-0011 已有设计（D2 检测规则 / D3 告警状态机），但**未落地到本设计文档**：

```sql
-- ADR-0011 D2（未纳入本设计）
detection_rules(rule_id, metric_key, comparator, threshold, window, severity, enabled)

-- ADR-0011 D3（未纳入本设计）
alerts(alert_id, rule_id, series_id, fired_at, cleared_at,
       acked_at, acked_by, state)   -- firing | acked | cleared
```

## 影响

- 「每日巡检发现异常」的**判定标准无处配置**——
  §10.5 举例「光功率降 3.2dB」算劣化，但阈值规矩没有存放位置
- 告警的**生命周期**（触发/确认/恢复）无法表达
- §10.5 的交叉验证无数据可依

## 建议方向

**直接采用 ADR-0011 D2/D3 的设计**，并补充本设计特有的内容：

1. **检测规则与既有 E/W/I 规则目录的关系**
   ADR-0011 已定「同构不同表」：
   - E/W/I 描述「导入数据质量缺陷」（`issues` 表，rule_version 锚定）
   - 检测规则描述「运行指标越限」（`alerts` 表）
   - **不混用 rule_version**（混用会让导入回归与检测演进互相锁死）

2. **规则的方向依赖 §5.3 的 `metric_keys.direction`**
   已设计 `higher_is_better / lower_is_better / neutral`——
   检测规则应复用它判断「越限方向」，不重复定义

3. **告警与运行状态（issue #22）的衔接**
   告警触发 → 是否更新 `resources.run_state`？需明确（建议：是，作为状态来源之一）

4. **告警的地图/拓扑呈现**（次要）
   §10.5 的 candidates 高亮可复用告警级别

## 评判标准

1. **可配置性**：不改代码能否新增一条阈值规则
2. **可复现性**：同数据同规则 → 同告警集（确定性，延续项目哲学）
3. **与 §10.5 的衔接**：`candidates` 能否用告警数据判定
4. **与 E/W/I 的隔离**：检测规则演进不应影响导入回归测试

## 默认方案（不能决定时采用）

**按 ADR-0011 D2/D3 原样落地**（该 ADR 已是「已接受」状态），
补充上述 4 点衔接说明。

```go
// TODO(design-v2): 告警与检测规则见 issue #23；
// 当前按 ADR-0011 D2/D3 实现，与 E/W/I 规则目录同构不同表。
```

## 处置指令

本项为**设计缺失**（非「两难选择」）：实施前必须补齐设计，
否则实施方只能靠猜，且猜错会静默致错。

1. **先补设计**：把本 issue 的设计结论回写 `docs/design/data-model-v1.md`
2. **可测的项要测**：给出量化对比（如存储规模、查询耗时、行数）
3. **不能决定时**：采用「默认方案」+ 代码 `TODO(design-v2): ...` 标记 +
   本 issue 回帖记录原因，供后续替换
4. **不要绕过**：本项缺失会导致后续所有分析结论不可信，不允许「先实现再说」
