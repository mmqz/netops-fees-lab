# [P2] 真实数据演示层级不足，拓扑看不出网络结构

来源：用户 2026-10-13 现场反馈（运行 v0.8.0 真实数据演示）+ 本地库直查复核

用户原话：

> **「数据的层级不够啊数据太少」**
> **「问题2有点没连上是端点设备」**

## 二、根因一：基站无上联关系（1193 个孤岛）

`uplink_to`（base_station → device）在设计 §4.2 中已定义，但演示数据**零条**。

原因链：
1. §12-B4 裁决「既有字段（归属A IP/名称）不自动派生关系」——**该裁决本身正确**
   （按名称匹配违反项目「禁止名称推断」红线）
2. 但演示数据也**没有提供显式的上联键列**
3. 结果：1,193 个真实基站**全部孤立**，地图上飘着、拓扑里连不上

**影响**：这是演示最直观的失败——1,198 个基站是 v0.8.0 的头号卖点，
但它们在图上是一盘散沙，看不出「基站—上联设备—传输—局站」的层级。

## 三、根因二：链路是「电路端点对」，不是网络拓扑

用户「**没连上是端点设备**」的判断**完全正确**。实测 `links` 表：

```
a_interface_id  z_interface_id  label     resource_id
if-1            if-2            CIR-001   res_...
if-3            if-4            CIR-002   res_...
if-5            if-6            CIR-003   res_...
```

即**每条链路 = 一条电路的两个端点接口**（物化规则见 `internal/sim/materialize.go`：
circuit 的 a_end/z_end → link）。

**后果**：拓扑画布上 10 条链路全是「端点—端点」直连，
**不表达任何真实网络连接**（设备间光缆、环网结构、上下联）。

## 四、量化对比

| 维度 | 当前 | 演示应有的量级 |
| --- | --- | --- |
| 后端资源 | 1,965 | 够（但 75% 孤立） |
| 工作台设备 | 30 | 够 |
| 工作台接口 | 20 | 偏少（30 设备仅 20 接口） |
| **工作台链路** | **10** | **应 ~30+（含真实互联）** |
| **基站上联** | **0** | **1,193 个基站应各有 uplink_to** |

## 五、建议

1. **补 `uplink_to` 演示数据**：在 `scripts/realdata/workbooks.py` 为基站生成
   显式上联键列（最近设备编码，按**经纬度最近邻**计算而非名称匹配——
   这样既满足「按坐标/显式键派生」又不违反红线）
2. **补设备间互联链路**：让工作台链路包含真实的设备互联（光缆/波道派生），
   而非只有电路端点对
3. **补 `serves` 边**（见 #40），让「设备→客户」直通
4. 若某类关系确实无法从公开数据构造，应在 `manifest.json` 说明并**降低该类型的演示占比**

## 验收

- [ ] 基站不再孤立（有 `uplink_to`）
- [ ] 工作台链路数反映真实互联（非仅电路端点对）
- [ ] 孤立资源占比显著下降（目标 < 30%）
- [ ] `manifest.json` 如实披露仍孤立的部分及原因

## 六、【补充实测】工作台物化丢弃 90 个真实端口，18/30 设备零接口

进一步直查工作台数据，发现比「链路只有 10 条」更根本的问题：

```
工作台设备           30
工作台接口           20      ← 全部由链路合成
接口数为 0 的设备     18 / 30 ← 60% 的设备是孤立点
有接口的设备         12

后端 port 资源        90      ← 完全未被物化使用
```

### 根因（代码核对 `internal/sim/materialize.go`）

```go
// L243
result.Counts.Interfaces = 2 * result.Counts.Links   // 接口 = 链路的 2 倍
```

接口**只从链路（电路端点）合成**，即：

```
10 条链路 × 2 = 20 接口   ✓ 与实测一致
90 个真实 port 资源        ✗ 被完全忽略
```

**因此 18 台设备（没有电路端点）接口数为 0**——在拓扑画布上就是飘着的孤立点。
这正是用户看到的现象与「**数据太少**」感受的直接来源。

### 为什么这是问题（而非「设计如此」）

物化规则源自 v0.5 的设备级沙盘（那时候确实只有 device/circuit）。
v0.7.0 把模型扩到 33 类型后，**materialize 没有同步扩展**——
这是 §12-B3「lab 保持现状」裁决的**副作用**：

| B3 裁决 | 本意 | 实际后果 |
| --- | --- | --- |
| lab 只服务设备级连通性推演 | 不物化光缆/业务等多层 | **连设备自己的端口也没物化** |

即「保持现状」被理解得过窄——**端口是设备自身属性，不是新增的跨层结构**。

### 建议

1. **物化纳入 port 资源**：把 90 个 port 变成设备的接口（设备自然有接口），
   而不是只从链路反推
2. 链路来源扩展：除电路端点对外，补设备互联（光缆/波道派生）
3. 若坚持「lab 只做设备级」，则应在 UI 明确标注
   「本视图仅含电路端点，不含设备端口」，避免被误读为数据缺失
4. 长期：评估 B3 裁决是否需要修订（#24）——多层沙盘可能才是演示所需
