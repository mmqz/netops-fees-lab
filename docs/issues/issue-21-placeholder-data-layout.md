# [设计决策] 占位数据的目录约定与生成器归属

关联：`docs/design/data-model-v1.md` §8（占位数据策略）

## 问题

占位数据（合成 + 公开数据）放哪？生成器放哪？
仓库已有：
- `testdata/` —— 合成测试数据（**入仓库**，`netopslab testdata` 可确定性再生成）
- `samples/` —— 真实电信样例（入仓库，有专门披露文档）
- `mapdata/` —— 地图数据引用（不入仓库，走 Release）

新增的占位数据（普通资源 + 时序指标 + 公开地理数据）如何归置？

## 候选方案

**方案 A：复用 `testdata/`**
- 生成物直接进现有 `testdata/`，命令扩展为 `netopslab testdata --profile <name>`
- 优点：无新目录；缺点：真实回归样例与占位数据混在一起

**方案 B：新增 `placeholder/`**
- 占位数据独立目录，与 `testdata/` 分离
- 优点：语义清晰（真实回归 vs 占位演示分得开）；缺点：新目录需约定

**方案 C：`testdata/placeholder/` 子目录**
- 复用父目录约定，内部再分

## 评判标准

1. **现有测试是否会被污染**：`testdata/expected-summary.json` 等
   回归基准是否依赖 `testdata/` 的完整清单
   （若依赖 → 新增文件会破坏基准 → 应选 B/C）
2. **公开数据的署名/许可标注**在哪里放最清晰（§8.4 要求）
3. **`.gitignore` 复杂度**

**第 1 条是可测的关键**：检查现有测试是否遍历 `testdata/` 全部文件。

## 默认方案（不能决定时采用）

**方案 C（`testdata/placeholder/`）**，理由：
- 保持 `testdata/` 作为「合成数据」的总语义
- 子目录隔离，不污染既有回归基准
- 公开数据的许可声明可放 `testdata/placeholder/LICENSE-NOTICE.md`

代码中标记：
```go
// TODO(design-v2): 占位数据目录约定见 issue #21；
// 当前生成到 testdata/placeholder/。
```

## 处置指令（给实施方）

**这不是「等人类裁决」的阻塞项，而是「你测试后择优」的决策项。**

1. **先做实验**：按下方「候选方案」各实现一个最小版本（可只在测试内验证，不必进主干）
2. **用数据选**：按「评判标准」量化对比，选胜出者
3. **不能决定时**：采用「默认方案」，并在代码中留 `TODO(design-v2): ...` 标记 +
   在本 issue 回帖记录「为何未能决定」，供后续替换
4. **无论选哪个**：把结论回写 `docs/design/data-model-v1.md` 对应小节（含决策理由）

> 原则：**可测的就测，不可测的用默认值并显式标记**——
> 不要让任何一项悬空导致实施卡住。
