# [设计决策] `belongs_to` 与 `housed_in` 是否合并

关联：`docs/design/data-model-v1.md` §4.2（空间归属）、§10.2（边的两种性质）

## 问题

设计中同时存在两个语义相近的空间关系：

| relation | 方向 | 设计语义 |
| --- | --- | --- |
| `belongs_to` | machine_room → site | 机房「容器归属」局站（**既有**，v10 落地） |
| `housed_in` | device → machine_room | 设备「物理位置」在机房（**新增**） |

二者是否应合并为一个 `located_in`？

## 候选方案

**方案 A：保留两个（区分语义）**
- `belongs_to` = 层级容器（谁包含谁）
- `housed_in` = 物理位置（谁放在哪）
- 优点：语义精确；缺点：查询时需同时考虑两者，AI 易混

**方案 B：合并为 `located_in`**
- 统一表达「A 位于 B 内」，容器与物理位置不再区分
- 优点：关系类型少、查询简单；缺点：丢失「容器」与「位置」的区分能力

**方案 C：保留两个但强约束层次**
- 两者都保留，但在 §10.2 层次表中把它们**标注为不同层差**，
  查询时按 `layers` 参数自然分离

## 评判标准（可量化）

1. **查询正确性**：同一测试图上，
   `GET /resources/{device}/traverse?direction=up` 能否稳定返回「机房 → 局站」完整链？
2. **查询性能**：两种方案下 10 万资源图的 traverse P95 耗时
3. **语义歧义**：构造边界用例（设备直接挂局站、机房跨局站），
   看哪种方案能无歧义表达
4. **迁移成本**：方案 B/C 对既有 v10 数据的影响

## 默认方案（不能决定时采用）

**方案 A（保留两个）**——因为 `belongs_to` 已是 v10 已落地语义，
改动它属于破坏性变更（违背 §10.10「不做破坏性变更」原则）。

代码中标记：

