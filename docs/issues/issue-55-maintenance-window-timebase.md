# [P1] v0.12.0 维护窗口抑制静默失效：窗口按墙钟建、检测按数据时间评估，时基不一致时 suppression 永不触发

来源：对 `e258543`（v0.12.0，R15 维护窗口）的功能级实测，2026-10-17
方法：受控对照实验（删告警 → 建窗口 → 重跑检测），三组实验交叉验证

---

## 一、现象

维护窗口（`/api/maintenance/windows`）创建成功、列表可见、时间范围正确覆盖当前时刻，
**但对新建告警完全没有任何抑制效果**，且回执里 `suppressed=0`，**无任何提示或警告**。

## 二、受控实验（三组交叉验证）

被测 series：`ser_a82cfe57`（`dr_loss_rx`，`packet_loss_rx_pct ≥ 1`），
资源 `res_0d1e9d89-bce7-47c0-b588-8fa21100e90b`（`大庆市传输设备01|xgei-1/1/1`）。

每组实验前都先 `delete from alerts where series_id = 'ser_a82cfe57-...'`，
确保该 finding "从未告警过"，从而必然走新建分支。

| 实验 | 维护窗口 | 数据时间（evaluatedAt） | findings | created | suppressed | 判定 |
| --- | --- | --- | --- | --- | --- | --- |
| **A** | 无 | `2026-10-12T00:00:00Z` | 4 | **1** | 0 | 基线：正常建告警 ✅ |
| **B** | `2026-10-17T00:53Z ~ 06:53Z`（**墙钟**，覆盖"现在"） | `2026-10-12T00:00:00Z` | 4 | **1** | **0** | ❌ **抑制未生效** |
| **C** | `2026-10-11T00:00Z ~ 10-13T00:00Z`（**覆盖数据时间**） | `2026-10-12T00:00:00Z` | 4 | **0** | **1** | ✅ 抑制生效 |

实验 C 的回执明细：

```json
{"ruleId":"dr_loss_rx","action":"suppressed","state":"",
 "resourceId":"res_0d1e9d89-bce7-47c0-b588-8fa21100e90b"}
```

告警总数在 C 中保持 3（未新建），在 A/B 中变为 4。

## 三、根因

`internal/detect/engine.go:322`

```go
if matchSuppressionWindow(supWindows, f.ResourceID, f.LastTS) != nil {
    res.Suppressed++
    ...
}
```

匹配用的是 **`f.LastTS`（数据时间戳）**，而不是当前墙钟时间。

而维护窗口由运维人员通过 `POST /api/maintenance/windows` **按墙钟**创建
（`startsAt`/`endsAt` 为 RFC3339，典型值就是"今天 22:00 到明天 02:00"）。

本库的 `evaluatedAt` 是 `2026-10-12T00:00:00Z`（数据里的最大时间），
比当前墙钟 `2026-10-17` 早 5 天。**两个时基不一致，窗口永远匹配不上。**

`matchSuppressionWindow` 本身实现正确（`Suppresses(resourceID, lastTS)` 语义清晰），
问题在于**调用方传入的是数据时间，而窗口是用墙钟定义的**——这在设计上没有对齐。

## 四、为什么这是缺陷而不是设计

1. **静默失败**：抑制没生效时不报错、不警告，`suppressed=0` 与"本来就没有需要抑制的告警"
   完全无法区分。运维人员会以为窗口保护已经生效。
2. **与确定性公理冲突**：系统的核心公理是"`ts` 来自数据，不用服务器时钟"。
   但维护窗口是**人类按墙钟做的计划**，它天然是墙钟语义。
   两者必须在某处显式桥接，当前没有任何桥接。
3. **演示/回放场景必然踩中**：这是本项目最常见的用法——导入历史数据（10-12 的指标），
   今天（10-17）按"今天"建维护窗口，然后重跑检测。**抑制 100% 失效。**
4. **不影响已有告警是正确的**：`engine.go:313-321` 里已有告警走 `UpdateFiringEvidence`
   后 `continue`，不经过抑制判断——这是对的（窗口"只挡新噪音，不改写历史"）。
   问题纯粹在新建分支的时间基准。

## 五、建议修复（三个方案）

### 方案 1（推荐）：窗口时间按数据时间解释

检测已有一个明确的"当前评估时刻" `evalTS`（即 `evaluatedAt`）。维护窗口若
**以数据时间语义**存储与比较，则：

```go
// 匹配用 evalTS（数据时间），与 f.LastTS 同基准
if matchSuppressionWindow(supWindows, f.ResourceID, f.LastTS) != nil
```

已是数据时间，**只需在文档/UI 明确"维护窗口时间 = 数据时间语义"**，
并在前端创建窗口时提示"按数据时间填写（当前数据时刻：2026-10-12T00:00Z）"。

优点：零代码逻辑改动，与确定性公理一致。
缺点：要求运维人员按数据时间填写，心智负担高。

### 方案 2：双时基支持

窗口记录同时存 `startsAt/endsAt`（墙钟，人用）与可选的 `dataStartsAt/dataEndsAt`（数据时间）。
匹配时二者其一命中即抑制。

优点：兼顾两种用法。缺点：表结构变更 + 语义复杂度上升。

### 方案 3（最小可用）：不匹配时给出可观测提示

在回执里增加 `suppressionSkippedReason` 字段，当存在活跃窗口但时基与数据时间
无交集时明确提示：

```json
{"suppressed":0,
 "suppressionNote":"2 个维护窗口处于墙钟激活期，但数据时间 2026-10-12T00:00Z 不在任何窗口内（数据时间与墙钟相差 5 天）"}
```

**即使采用方案 1 或 2，也建议同时加这条提示**——静默失败本身就该消除。

## 六、验收标准

1. **明确时基语义**：API 文档 `docs/api.md` 与前端 UI 都写明维护窗口的时间基准是
   **墙钟**还是**数据时间**，不允许含糊；
2. 若选方案 1：前端创建窗口时展示"当前数据时刻"并预填；
3. 若选方案 2：两种时基各自可验证；
4. **必须**：存在活跃窗口但抑制未触发时，回执给出可观测原因（消除静默失败）；
5. 补一条契约测试：`dataTime ∈ window ∧ finding 新建 → suppressed=1, created=0`；
   `dataTime ∉ window → created=1`（当前实测正是后者，B 组实验）。
6. 回归：已有告警不被窗口改写（`engine.go:313-321` 的行为保持）。
