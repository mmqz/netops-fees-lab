# [设计缺失] 状态模型：台账状态与运行状态未区分

关联：`docs/design/data-model-v1.md` §10.5（根因判定）、§3.2（资源字段）

## 问题

现设计只用 `resources.status` 一个字段表达状态，取值是**台账枚举**
（`在网 / 停用 / 在建 / 退网`，见 `mapping.StatusEnum`）。

但 §10.5 的根因判定写的是「资源 `status` 为故障」——
**「故障」不在上述枚举中**，该判据无法执行。

根因：**台账状态与运行状态是两个不同维度**，被混用在一个字段：

| 维度 | 取值 | 来源 | 变化频率 |
| --- | --- | --- | --- |
| **台账状态**（生命周期） | 在网 / 停用 / 在建 / 退网 | 资源表导入 | 低（月/季） |
| **运行状态**（实时） | up / down / 告警 / 维护 / 未知 | 告警/巡检数据 | 高（分钟/小时） |

**实例**：`sim/materialize.go:17` 的现有处理印证了这个混淆——
它把台账的「在网」映射为虚拟设备的 `up`，其余全部映射为 `down`，
即**用台账状态冒充运行状态**。

## 影响

- §10.5 的 `candidates`（根因候选）判定**无依据**，会全部判错
- 无法表达「设备台账在网，但当前链路中断」这一最常见的运维状态
- 每日巡检的「发现异常」缺少状态维度（只有指标，没有状态）

## 建议方向

**引入独立的运行状态维度**，候选方案：

**方案 A：`resource_status` 独立表（时序或快照）**
```sql
resource_status(
  resource_id TEXT NOT NULL REFERENCES resources(id),
  ts          TEXT NOT NULL,          -- 状态生效时间
  run_state   TEXT NOT NULL,          -- up|down|degraded|maintenance|unknown
  source      TEXT,                   -- 来源：alert|poll|manual
  PRIMARY KEY (resource_id, ts)
)
```
- 与 §5 的时序表同构（状态也是一种时序量）

**方案 B：`resources` 加运行状态列（快照）**
```sql
ALTER TABLE resources ADD COLUMN run_state TEXT;      -- 仅当前值
ALTER TABLE resources ADD COLUMN run_state_at TEXT;   -- 状态时刻
```
- 简单，但丢失状态历史

**方案 C：A + B 混合（历史 + 快照）**
- 时序表存历史，`resources` 冗余当前值加速查询

## 评判标准

1. **§10.5 可执行性**：给定「台账在网 + 运行 down」，根因判定能否正确工作
2. **状态历史可查**：「该设备过去 7 天是否抖动」能否回答
3. **查询性能**：全库状态统计（多少设备 down）P95
4. **与台账状态的隔离**：台账状态变更（W005 属性变更流）不应影响运行状态
