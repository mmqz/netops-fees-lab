# [设计决策] 端口性能数据挂哪一层：端口资源 vs 设备+scope

关联：`docs/design/data-model-v1.md` §5.4 D5、§10.5（根因判定依赖层次正确）

## 问题

真实端口表的性能数据是**端口级**的（含「设备IP + 端口名」两列）。
这些指标应挂在哪一层？

## 候选方案

**方案 A：挂端口资源（推荐候选）**
```sql
-- port 已是既有资源类型（v7 落地，复合键 device_name|port_name）
metric_series(resource_id = <port 资源 id>, metric_key = 'optical_power_rx_dbm', scope = NULL)
```
- 优点：层次正确（§10.2 层次表中 port 属 L1）；根因可精确定位到端口
- 缺点：`metric_series` 行数 = 端口数 × 指标数（端口远多于设备）

**方案 B：挂设备 + scope 区分**
```sql
metric_series(resource_id = <device 资源 id>, metric_key = '...', scope = 'gei_1/2')
```
- 优点：`metric_series` 行数少
- 缺点：**scope 是字符串，无法被图查询 JOIN**；
  §10.5 根因判定要「从异常端口找到承载电路」，端口不在图里就断链

**方案 C：混合**
- 需要参与图查询的指标挂端口；纯统计类指标挂设备
- 优点：兼顾；缺点：规则复杂，使用者需判断每个指标挂哪

## 评判标准（可量化）

1. **图查询连通性（最关键）**：
   构造「端口 → 纤芯 → 光缆 → 局站」链路，
   断言 `GET /resources/{port}/traverse?direction=up` 能到达局站层
   （方案 B 必然失败，因 scope 不是图节点）
2. **存储规模**：1 万设备 × 20 端口 × 10 指标 × 365 天，
   两种方案的 `metric_series` 与 `metrics` 行数对比
3. **查询性能**：单设备全部端口的最新指标查询 P95
4. **§10.5 根因追溯准确性**：
   「某端口光功率劣化 → 影响哪些业务」能否收敛到正确候选

## 默认方案（不能决定时采用）

**方案 A（挂端口资源）**——因为 §10.5 的根因追溯**依赖端点是图节点**，
方案 B 会使追溯在端口层断链，违背设计目标。
