# [设计缺失] 导入映射配置管理

关联：`docs/design/data-model-v1.md` §9.2、既有的 `analyze → suggest → import` 通道

## 问题

设计说「各表导入只需新增 `mapping.Specs` 条目」，但：

1. **45 类资源 = 45 份映射配置**，放哪？
   - 现在 `mapping.Specs` 是**代码里的硬编码**
   - 45 类会让 `schema.go` 膨胀到数千行
2. **真实表头千变万化**：
   - 同一类型不同地市/不同网管版本的表头可能不同
   - 是否需要**用户可配置**的映射（JSON 文件）而非代码？
3. **映射的复用**：
   - 现有流程是「analyze 产出 suggestedMapping → 人工确认 → import」
   - 每日导入若每次都要人工确认映射，**无法自动化**

## 关键矛盾

**每日自动导入 vs 人工确认映射**：

现有流程（`ImportWizard`）要求人工确认映射后才导入；
但用户目标是「**每天只要导入表格，就能完成日常巡检**」——需要无人值守。

## 影响

- 每日导入无法自动化（每次都卡在映射确认）
- 45 份映射的维护成本未评估
- 网管表头变更时，如何感知（导入失败？静默错映射？）

## 建议方向

**方案 A：映射模板持久化**
```
每个「数据源 + 表头指纹」对应一份已确认映射，存库：
  mapping_templates(template_id, source_name, header_fingerprint, mapping_json, confirmed_at)
导入时按表头指纹自动匹配模板 → 命中即自动导入，未命中才要求确认
```
- 优点：支持无人值守，且能感知表头变化（未命中 = 表头变了）
- 这是「每日自动导入」的关键前提

**方案 B：映射写死在代码**
- 45 份映射硬编码
- 缺点：表头变化需改代码发版

**方案 C：配置文件**
- 映射放 YAML/JSON 文件，随部署分发

## 评判标准

1. **无人值守可行性**（最关键）：连续 7 天导入同一网管导出，
   断言**无需人工介入**
2. **表头变更感知**：表头增删列时，断言导入**报错或告警**（不静默错映）
3. **维护成本**：新增一个类型/一份新表头的改动量
4. **确定性**：同表头同模板 → 同映射结果

**第 1 条是本设计的验收前提**（用户目标的核心）。

## 默认方案（不能决定时采用）

**方案 A（映射模板持久化）**，因为：
- 用户目标「每天导入」**必须有无人值守**
- 表头指纹天然提供「网管改格式」的检测能力
- 与既有 `import_batches.mapping` 字段（已存确认映射）可衔接

```go
// TODO(design-v2): 映射模板持久化见 issue #28；
// 当前沿用人工确认流程；自动导入需先实现模板匹配。
```
