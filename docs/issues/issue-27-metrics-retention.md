# [设计缺失] 时序数据量级与保留/归档策略未设计

关联：`docs/design/data-model-v1.md` §5.3（metrics 表）

## 问题

设计定义了 `metrics` 表，但**没有量级估算与保留策略**。

**规模估算**（按 §3.2 的类型规模）：

```
场景：1 万设备 × 平均 20 端口 = 20 万端口
      每端口 10 个指标 → 200 万条序列
      每日 1 点 × 365 天
      = 200 万 × 365 = 7.3 亿行
```

**7.3 亿行的 SQLite 窄表**——需要明确：

1. 单文件 SQLite 能否承载（已知上限约 281 TB，但**性能**是问题）
2. 每日导入这批数据耗时多少（批量 upsert）
3. 是否需要保留策略（原始 N 天 + 聚合永久）
4. 是否需要归档/分库

## 影响

- 越晚发现，改造成本越高（数据已写入）
- 每日巡检查询若扫全表会超时（§5.5 Q2 的全库扫描）
- 单二进制/单文件的产品定位受影响（是否需要拆库）

## 建议方向

**方案 A：分层保留（推荐）**
```
原始点：保留 90 天
日聚合（avg/min/max）：永久
周聚合：永久（更旧的数据）
```
- 90 天原始 = 200 万 × 90 = 1.8 亿行（仍大但可接受）
- 聚合表行数 = 序列数 × 天数 / 聚合粒度（小得多）

**方案 B：按需采集**
- 只对关键指标采集原始点（如仅光功率），其余只存日聚合

**方案 C：分库**
- 每专业域或每时间分区一个 DB 文件
- 破坏「单二进制/单文件」定位，代价大

## 评判标准

1. **导入耗时**：单日全量（约 20 万行）导入 P95（目标 < 30s）
2. **巡检查询耗时**：§5.5 Q2 全库扫描 P95（目标 < 5s）
3. **DB 体积**：1 年后单文件大小
4. **产品定位**：是否仍满足「单文件可拷贝」

**第 1、2 条必须先实测**（用合成数据跑），再决定是否需要聚合/保留策略。

- 阶段 1：只存原始点，实测导入与查询耗时
