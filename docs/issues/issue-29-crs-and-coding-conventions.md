# [设计缺失] 坐标系统一与资源编码规范

关联：`docs/design/data-model-v1.md` §3.2（各类型字段）

## 问题

新增资源多数带地理坐标（光缆、接头盒、人井、杆路、基站、局站、专线端点），
但设计未规定：

### 1. 坐标系（CRS）

项目现状（v0.6.3/v0.6.4 已存在双变体）：
- `geo_lat` / `geo_lng` 存 **WGS84**（设备地理字段，v6）
- 地图叠加数据生成了 **WGS84 与 GCJ-02 双变体**
  （`hlj-admin-areas.geojson.gz` / `hlj-*-gcj.geojson.gz`）
- 渲染时 WGS84→GCJ-02 转换在客户端做

**新增资源的坐标该存哪个 CRS？** 设计未写。

### 2. 资源编码规范

设计的自然键涉及编码，但**编码由谁定义**未明确：

| 类型 | 自然键 | 问题 |
| --- | --- | --- |
| `optical_cable` | `cable_code` | 网管导出的是「光缆名称」，需转编码？ |
| `fiber` | `cable_code\|fiber_no` | 纤芯号格式（`1` vs `01` vs `1/12`）？ |
| `ring` | `ring_code` | 基站表的 `环/链` 值是 `环1`，不是编码 |
| `leased_line` | `line_code` | 专线有 `专线编号`/`集团STN编号`/`互联网专线编号` 三个候选 |

## 影响

- CRS 不统一 → **坐标偏移数百米**（WGS84 与 GCJ-02 差约 500m），
  地图上设备落点错误
- 编码不规范 → **同一资源被识别为多个**（`1` 与 `01` 不同键），
  或不同资源被合并
- 复合键拼接（既有 `|` 约定）遇到值含 `|` 时的碰撞（既有文档已声明接受）

## 建议方向

### CRS

**统一存 WGS84**（与既有 `geo_lat/lng` 一致），
渲染时按底图 CRS 转换（既有能力）。

理由：
- 已有实现（v6 设备字段 + 客户端转换）
- WGS84 是国际标准，转换到 GCJ-02 有成熟算法（既有 `geoBasemap` 已实现）
- 反向（GCJ→WGS84）是有损的，不应作为存储格式

### 编码

**逐类型定义编码规则**，需明确：
1. 编码来源列（网管的哪一列）
2. 规范化规则（去空格、统一大小写、前导零处理）
3. 无编码时的兜底（参考既有 `base_station` 的条件自然键：编码空 → 名称兜底 + W004 警告）

## 评判标准

1. **坐标一致性**：同一物理点从不同表导入，落点偏差 < 10m
2. **编码稳定性**：同一资源多次导入（含格式微变），键不变
3. **兜底可感知**：无编码时产生警告而非静默（沿用 W004 模式）

## 默认方案（不能决定时采用）

**CRS：统一 WGS84**
**编码：沿用既有模式**——
- 有编码列 → 用编码（规范化：trim + 统一大写）
- 无编码列 → 名称兜底 + 警告（复用 W004 条件自然键机制）
