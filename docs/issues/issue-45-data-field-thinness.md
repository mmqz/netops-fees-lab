# [P2] 演示数据字段厚度不足：98% 资源无状态、基站字段远少于真实表、geo 仅存 JSON 字符串

来源：用户 2026-10-13 现场反馈「**数据的层级不够啊数据太少**」+ 本地库直查复核

#42 讲的是**关系层**薄（75% 孤立）。本 issue 讲**字段层**薄——两者叠加才是「数据太少」的完整体感。

---

## 一、98% 的资源没有状态（实测）

```
有 status 的资源    40 / 1965   （2.0%）
无状态（NULL）     1925 / 1965   （98.0%）

有状态的仅两类：device 30（在网）、circuit 10（在网）
其余 29 类全部 NULL → UI 资源浏览页整列显示「未知」
```

**影响**：资源浏览页第一屏（默认按编码排序）**全是基站，状态列全是「未知」**，
用户第一眼看到的就是一片灰色「未知」——这是「数据太少」最直观的来源。

## 二、基站字段远少于用户真实表（设计已记录真实结构）

`docs/design/data-model-v1.md:196` 记录的真实基站表字段：

```
| base_station | 基站 | 条件键（编码 / 地市|名称） |
  基站类型、电联共享、环/链、归属A |  ← 设计已确认这些字段存在
```

但 `testdata/realdata/base_stations.xlsx` **只有 4 列**：

```
基站编码 | 无线基站名称 | 基站类型 | 地市
```

**丢失的字段**：

| 字段 | 设计中的用途 | 丢失后果 |
| --- | --- | --- |
| **环/链** | 保护方式（`ring` 资源 / `member_of_ring`） | 环网结构无法演示 |
| **归属A IP/名称/端口** | `uplink_to`（设计 §4.2 标注 **P0**） | **1,193 基站全部孤立**（见 #42） |
| 电联共享 | 共建共享场景 | 无法演示 |

**关键矛盾**：设计把 `uplink_to` 定为 **P0**，但演示数据的源表里
**连字段都没有**——不是「关系没派生」，而是「源头数据就没提供」。

入库侧实测（`base_station` 的 attributes）：

```json
{"base_station_name": "基站·哈尔滨市·001",
 "base_station_type": "5G",
 "city": "哈尔滨"}
```

仅 3 个键，其中 `base_station_name` 还与 `name` 列重复。

## 三、geo 只以 JSON 字符串存在，`resources` 表无地理列

`resources` 表结构实测：

```
id, resource_type, natural_key, name, attributes, status,
first_batch_id, created_at, updated_at, run_state, run_state_at
```

**没有任何 geo 列**。坐标只存在于 `attributes` JSON 里，且是**字符串**：

```json
{"geo_lat": "48.45402", "geo_lng": "125.11985"}
```

而工作台侧 `virtual_devices` **有** `geo_lat`/`geo_lng` **数值列**。
两层不一致，且 `resources` 侧：

- 无法建空间索引（R-Tree）
- 无法做 SQL 级空间查询（最近邻、半径）
- 地图渲染需逐行解析 JSON 字符串并转换类型

实测只有 **90 个**资源带坐标（port 90 个），
device 的坐标在 attributes 里（30 个），其余类型无坐标。

## 四、字段厚度对比（源表 vs 入库）

| 工作簿 | 源表列数 | 入库 attributes | 说明 |
| --- | --- | --- | --- |
| devices | 12 | 9 | 编码/名称/状态→专用列，正常 |
| ports | 14 | 11 | 正常 |
| sites | 4 | 2 | 正常（编号/名称→专用列） |
| machine_rooms | 5 | 3 | 正常 |
| **base_stations** | **4** | **3** | **源表本身就薄（真实表 13–14 列）** |

**结论**：入库映射没问题，问题在**生成器输出的源数据太薄**。

## 五、建议

1. **基站表补列**：按设计 §3.2 记录的**真实表结构**生成
   （环/链、归属A IP/名称/端口、电联共享），
   即使值需模拟——**字段存在才能演示 P0 的 `uplink_to`**
2. **补 status**：为各类资源生成符合枚举的状态值
   （在网/停用/在建/退网），至少让主要类型有值
3. **geo 提升为列**：`resources` 增 `geo_lat`/`geo_lng`（REAL）+ 空间索引，
   与 `virtual_devices` 对齐；顺带解决 #29 的 CRS 统一
4. **补足字段厚度**：让各类型的 attributes 接近真实表列数，
   否则「33 类型」只是空壳

## 验收

- [ ] 无 status 的资源占比显著下降（目标 < 20%）
- [ ] `base_stations.xlsx` 含 环/链 与 归属A 列（值可为模拟）
- [ ] `resources` 有 geo 列且可做空间查询
- [ ] 主要类型的 attributes 字段数与真实表结构匹配
