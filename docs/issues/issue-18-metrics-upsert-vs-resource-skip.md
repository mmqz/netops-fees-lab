# [设计决策] 时序 upsert 与资源 skip 的语义差异是否可接受

关联：`docs/design/data-model-v1.md` §5.4 D3、§4（既有幂等语义）

## 问题

项目既有的重导语义是 **skip**（同键重导 → 跳过，属性差异进人工确认队列 W005）。
但设计中的时序存储采用 **upsert**（`PRIMARY KEY (series_id, ts)` + `INSERT OR REPLACE`）。

**同一系统内两种重导语义不一致**，是否可接受？

## 背景差异

| | 资源（既有） | 时序点（设计） |
| --- | --- | --- |
| 语义 | **身份**语义（同键=同资源） | **值**语义（同时间同指标的最新值=真值） |
| 重导行为 | skip（不改库，差异待确认） | upsert（覆盖） |
| 理由 | 属性变更需人工确认，防静默改台账 | 重新采集的同一时刻数据应覆盖 |

## 候选方案

**方案 A：两种语义并存**（设计现状）
- 资源 skip / 时序 upsert
- 优点：各自贴合语义；缺点：使用者需记住两套规则

**方案 B：时序也 skip**
- 同时刻同值 → skip；同时刻不同值 → 进确认队列
- 优点：语义统一；缺点：性能数据每天全量重导，会产生海量确认项（不可用）

**方案 C：时序 upsert + 变更留痕**
- 覆盖写，但把被覆盖的旧值记入变更表
- 优点：语义清晰且有审计；缺点：表膨胀

## 评判标准（可量化）

1. **幂等性测试**：同一份数据连续导入 3 次，
   断言 `SELECT COUNT(*) FROM metrics` 不变（A/C 应通过，B 会因确认队列失败）
2. **准确性测试**：同 `(series_id, ts)` 导入不同值，断言最终值为**最后一次导入的值**
3. **存储开销**：C 方案在 60 天数据下的额外行数（预估值 vs 实测）
4. **使用者混淆度**：能否用一句话向使用者说明白两种语义的边界

## 默认方案（不能决定时采用）

**方案 A（两种语义并存）**，并在文档中**显式声明边界**：

> 资源 = 身份语义（skip + 人工确认）
> 时序 = 值语义（upsert 覆盖）
