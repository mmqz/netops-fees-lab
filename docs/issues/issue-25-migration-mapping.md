# [设计缺失] 既有 8 类数据向新层次模型的迁移映射未定义

关联：`docs/design/data-model-v1.md` §9（实施路径）、§3（45 类资源）

## 问题

既有库有 **8 类资源**（v13）与 **4 种关系**，扩容到 45 类 / 32 种后，
**既有数据如何映射到新层次模型？** 设计文档未定义。

具体未决点：

| 既有 | 新模型中的处理 | 未决问题 |
| --- | --- | --- |
| `base_station` 的 `环/链` 字段 | 是否提升为 `ring` 资源 + `member_of_ring` 关系？ | 字段值形如 `环1`，需解析规则 |
| `base_station` 的 `归属A IP/名称/端口` | 是否派生 `uplink_to` 关系？ | 需按 IP/名称匹配设备——**但项目红线禁止按名称推断关系** |
| `circuit` | 同时是「传输层电路」和「业务专线」？ | 是否拆分为 `circuit` + `leased_line`？ |
| `machine_room` 的 `belongs_to` | 与新 `housed_in` 的关系 | 见 issue #17 |
| `port` | 保持端口级 | 见 issue #19 |
| `ptp_port` | 保持 | — |
| `ip_pool` / `site` | 保持 | — |

## 关键冲突

**`base_station.归属A` 派生 `uplink_to` 与项目红线冲突**：

> 项目既有红线：「**绝不从名称相似度推断关系**」
（`docs/data-model.md` §3，`relations` 表设计说明）

从「归属A名称」派生关系就是按名称匹配，**违反红线**。
需要明确：是用「归属A IP」精确匹配（可行），还是只做候选提示由人工确认？

## 影响

- 迁移时既有数据可能**丢失语义**（如 `环/链` 字段被忽略）
- 若擅自按名称派生关系，会**破坏项目红线**且产生错误关系
- 既有测试的 fixture 可能需要更新（但不应破坏断言语义）

## 建议方向

1. **逐类型给出映射表**：既有类型 → 新模型中的类型/字段/关系
2. **明确「不迁移」的字段**：哪些既有字段在新模型中无对应（如 `环/链`）
3. **关系派生遵守红线**：只能用**精确键匹配**（IP、编码），
   名称匹配只生成**候选提示**（类似 W005/W006 的人工确认流）
4. **迁移不破坏既有断言**：v1–v13 的迁移测试必须继续通过

## 评判标准

1. **数据完整性**：迁移前后资源数、关系数、属性值可核对
2. **红线遵守**：无任何基于名称相似度的自动关系派生
3. **既有测试**：v1–v13 迁移测试与 fixture 全绿
4. **可回滚**：迁移失败可恢复到迁移前状态

## 默认方案（不能决定时采用）

**保守迁移**：
- 既有 8 类资源的**类型与字段全部保留**（不动）
- **不自动派生新关系**（`member_of_ring` / `uplink_to` 都不从既有数据自动生成）
- 新关系只能来自**新的导入数据**（含关系列的表）
- `环/链` 等字段保持为 `attributes` 普通字段，不提升为资源

代码中标记：
```go
// TODO(design-v2): 既有数据的层次映射见 issue #25；
// 当前保守迁移：既有类型不动，新关系仅由新导入数据产生。
```

1. **先补设计**：把本 issue 的设计结论回写 `docs/design/data-model-v1.md`
