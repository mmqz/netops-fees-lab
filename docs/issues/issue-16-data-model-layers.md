# 数据模型缺层：拓扑只有 8 类资源 / 4 种关系，无法表达业务层与保护结构

## 背景

以「本地云网运维 + AI 拓扑推演」为目标使用本项目时，发现核心瓶颈**不是表格导入能力**
（导入只是映射配置，任何表头都能接），而是**数据模型缺少网络分层**。

导入通道完备（`analyze → suggest → import`、幂等重导、13 条质量规则、来源谱系），
但**图中只有节点和一条边类型**，导致业务层与保护结构无法表达、无法分析。

## 现状（v0.6.4 实测）

### 资源类型：8 种（`internal/domain/enums.go:11-18`）

```
device  ip_pool  circuit  port  base_station  site  machine_room  ptp_port
```

### 关系类型：4 种（`internal/domain/enums.go:57-60`）

```
assigned_to  // ip_pool → device
a_end        // circuit → device
z_end        // circuit → device
belongs_to   // machine_room → site（容器归属）
```

四种关系**全部是「资源 A 引用资源 B」的点对点外键**，没有一种能表达：
- 两台设备之间是**环网还是链形**（保护方式）
- 一条电路**由哪些光路/波道承载**（承载层次）
- 一个基站**归属哪个环**（汇聚结构）

### 实际导入规模（演示库）

```
resources:  circuit 31 / device 37 / ip_pool 16   （仅 3 类有数据）
relations:  a_end 31 / z_end 31 / assigned_to 15  （belongs_to 0）
```

## 四层模型对照

| 层 | 应表达 | 现状 | 缺口 |
| --- | --- | --- | --- |
| **业务层** | 客户专线、业务实例、承载业务 | `circuit` 仅有 a_end/z_end 两端引用 | **无客户、无业务类型、无带宽、无保护级别** |
| **逻辑层** | 环网/链形、汇聚结构、IGP 域 | 无 | **完全没有** |
| **传输层** | 电路、波道、光路 | `circuit` 与业务层混用同一张表 | **无层次区分** |
| **物理层** | 设备、端口、光缆、纤芯、ODF | `device` / `port` | **无光缆/纤芯/ODF** |

## 具体缺失（按可验证的字段）

### 1. 业务层信息被丢弃

实际专线表有 **23 列**（已确认的真实表头）：

```
级别 / 业务类型 / 组网方式 / 专线名称 / 专线编号 / 集团STN编号 /
互联网专线编号 / 客户IP掩码 / 客户名称 / A端装机地址 / Z端装机地址 /
A端IP / A端名称 / A端端口 / A端VLAN ID / A端装机经纬度 /
Z端IP / Z端名称 / Z端端口 / Z端VLAN ID / 协议带宽(Mbps) / 工单号
```

当前 `circuit` 类型只保留 a_end/z_end 两端引用与少量属性，**以下信息无处存放**：
- `客户名称` —— 无法按客户聚合（「某客户有多少条专线」答不了）
- `协议带宽` —— 无容量维度
- `A/Z端 VLAN ID` —— 无二层信息
- `A端装机经纬度` —— 专线本身的地理坐标未利用

### 2. 保护方式无处建模

基站表有 `环/链` 列（组网方式），描述该基站是**环网接入**还是**链形接入**。
环网存在保护倒换、链形无保护——**两者在故障影响分析中结论完全不同**，
但当前模型对二者一视同仁，分析结果失真。

### 3. 基站上联关系未派生

基站表含 `归属A IP` / `归属A名称` / `归属A端口`，描述基站的**上联设备与端口**。
这是**业务层到传输层的挂接关系**，当前未建立任何关系记录，
导致「断一条链路影响哪些基站」只能靠 IP 前缀猜测（项目明确拒绝按名称/前缀推断关系）。

### 4. 物理层资源缺失

光缆、纤芯、ODF、接头盒在 IPRAN 运维中是**故障定位的物理根因层**，
当前 schema 完全没有对应表。

## 影响

- **影响分析只能回答连通性**（A 到 B 通不通），**回答不了业务影响**（哪些客户/基站受损）
- **保护结构不可见**：环网断一条边有保护、链形断一条边即中断，模型区分不了
- **层次穿透不可做**：无法从「业务故障」下钻到「物理根因」（哪段光缆）
- 外部智能体（经 MCP）拿到的图**信息量不足**，只能做连通性推理

## 建议方向（讨论用，非本轮实施）

### 资源类型扩展

| 新增类型 | 来源 | 优先级 |
| --- | --- | --- |
| `customer`（客户） | 专线表 `客户名称` | P1 |
| `service`（业务实例） | 专线表 `业务类型` + 编号 | P1 |
| `ring`（环网） | 基站表 `环/链` + 汇聚结构派生 | P2 |
| `optical_cable`（光缆段） | 待数据源 | P3 |
| `fiber`（纤芯） | 待数据源 | P3 |
| `odf`（光配线架） | 待数据源 | P3 |
| `board`（板卡/槽位） | 待数据源 | P3 |

### 关系类型扩展（与 ADR-0011 D6 呼应）

```
serves       // 基站/设备 → 客户或业务（承载业务）
depends_on   // 业务 → 承载它的电路/光路（层次下钻）
protected_by // 链路 → 环网（保护关系） 或 链路 → 保护组
carried_by   // 电路 → 光路/波道（传输层承载）
connects     // 光缆 → 设备/ODF（物理连接）
```

### 与 ADR-0011 的关系

ADR-0011 D6 已提出 `serves` 与 `depends_on` 两个关系类型，并明确
「从导入的 port/base_station sheet 的既有列（上联 IP/网关/客户编码）物化」。
本 issue 是该决策的**证据补充与范围扩展**：不仅缺这两个关系，还缺整个层次模型。

## 关于导入通道的说明

**本 issue 不要求新增导入功能。** 导入通道已完备（`analyze`/`import`/`mapping`），
任何表头都能通过映射配置接入。真正的阻塞点是：

1. **没有存放位置** —— 例如 60 列性能数据、23 列业务字段在 schema 中无对应列/表
2. **没有关系类型** —— 例如环/链保护关系无法表达

schema 定下来之后，各表导入只需新增 `mapping.Specs` 条目（映射配置），
不需要为每张表开发专门的导入流程。

## 验收标准（供后续实施参考）

- [ ] 业务层可表达：客户、业务类型、带宽、保护级别
- [ ] 保护结构可表达：环网/链形可区分，故障影响分析能识别保护倒挂
- [ ] 上联关系可派生：基站 → 归属设备的挂接关系从既有列物化
- [ ] 物理层预留：光缆/纤芯/ODF 的 schema 位置已定义（可暂不导入）
- [ ] 层次下钻可做：业务 → 传输 → 物理 的正向与反向查询
- [ ] 既有 8 类资源与 4 种关系的兼容性保持（迁移不破坏现有数据）

## 备注

- 涉密数据无法提供，本 issue 的数据依据为**已确认的真实表头结构**（列名，无值）
- 待真实数据可获取后，按 schema 直接导入，无需改造导入通道
