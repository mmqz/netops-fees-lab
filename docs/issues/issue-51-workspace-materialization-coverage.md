# [P1] 仿真工作台只物化 device：32 类资源中 31 类闲置，1,961 条数据被丢弃

来源：用户 2026-10-15 现场质疑

用户原话：

> **「设备 30 接口 32 链路 16，问题是模拟数据只有这些啊？没有你说的 1991 那么多」**

**用户的观察揭示了两个层次的认知错位——且这个错位本身就是缺陷。**

---

## 一、事实：两层数据，量级差 66 倍

```
资源库 resources        1,991 条 / 32 类   ← run.ps1 与概览页显示的是这个
仿真工作台 virtual_*       30 台设备       ← 拓扑画布头部显示的是这个
```

### 实测：物化的输入只有 `device` 一类

```sql
select r.resource_type, count(distinct vd.resource_id)
from virtual_devices vd join resources r on r.id = vd.resource_id
group by 1;
→ device 30        ← 仅此一类
```

### 被闲置的 31 类（1,961 条）

| 类型 | 数量 | 本应参与 |
| --- | --- | --- |
| `base_station` | **1,198** | 接入层，拓扑上的无线侧节点 |
| `port` | 90 | 接口（当前 32 个接口是从链路反推的，非真实端口） |
| `fiber` | 56 | 纤芯（L2 物理层） |
| `splice_box` | 46 | 接头盒（物理锚点） |
| `circuit` | 32 | 业务电路（L3） |
| `cable_segment` | 23 | 光缆段（L2 物理） |
| `pon_port` | 20 | PON 口（接入） |
| `odf` / `rack` | 各 15 | 光配线架 / 机架（L0-L2） |
| `manhole` | 14 | 人井 |
| `otn_och` | 14 | OTN 波道（L3） |
| `customer` | 12 | 客户（L6 业务） |
| `onu` | 10 | ONU（接入） |
| `service` | 8 | 业务实例（L6） |
| `leased_line` | 6 | 专线（L6） |
| …其余 18 类 | 各 2-7 | |

**即：1,961 条数据（98.5%）存在于库中，但从不进入拓扑视图。**

## 二、根因：物化规则停留在 v0.5 时代

`internal/sim/materialize.go` 的物化输入：

```go
// 设备：device types
// 链路：circuit.a_end/z_end（或 v0.11 起的光缆走廊锚点链）
```

**只有 device 与 circuit 两类参与**——这是 v0.5 时代的数据模型（当时确实只有这两类）。
v0.7 把数据模型扩到 33 类型，但**物化从未跟进**。

这与 issue #24（lab 与扩容模型的关系）、#49（链路分层）**同源**：
- #49 修了「链路怎么连」
- **但没修「哪些资源该进工作台」**

## 三、影响：不只是「数量少」，而是「拓扑缺层」

当前拓扑画布上只有 L1（设备）一层。用户的核心目标是**从表象追溯真实故障来源**：

```
目标链路：
  客户专线 → 业务 → 电路 → 波道 → 光缆段 → 端口 → 设备
                ↑                              ↑
           L6 业务层                      L1 设备层

当前画布：只有 L1
  → 基站故障看不出影响哪些客户
  → 光缆中断看不出波及哪些业务
  → 影响分析（#49 的 impact 端点）在画布上无法呈现
```

**用户的直观感受「数据只有这些」是正确的**——尽管库里躺着 1,991 条。

## 四、修复方向

### 4.1 扩展物化输入（核心）

按层次映射到工作台实体：

```
资源类型              工作台表示
─────────────────────────────────────────
device            →  虚拟设备（已有）
port / pon_port   →  虚拟接口（替代当前从链路反推）
cable_segment     →  虚拟链路（物理层，已有 #49）
optical_cable     →  链路的分组/走廊
otn_och           →  逻辑链路（业务承载层）
base_station      →  接入节点（无线侧）
customer          →  端点节点（业务侧）
```

### 4.2 分层可见性

工作台应支持**按层显示/隐藏**（与 #49 方案 C 呼应）：

```
图层开关：[物理层] [传输层] [业务层] [接入层]
  物理层：设备 + 光缆段 + 接头盒
  传输层：波道 + 电路
  业务层：客户 + 专线 + 业务实例
  接入层：基站 + BBU/RRU + OLT/ONU
```

### 4.3 规模保护

1,198 个基站全量渲染会压垮画布（与 #50 同源问题）。需：
- 视口裁剪 / 聚簇（GeoCanvas 已有聚簇机制，TopologyCanvas 需补）
- 或默认只显示**与当前选中实体相关的子图**

## 五、验收

- [ ] 工作台物化覆盖 ≥ 8 个资源类型（当前 1 个）
- [ ] 拓扑画布可显示业务层节点（客户/专线），且与设备层有可见路径
- [ ] 提供分层显示开关（物理/传输/业务/接入）
- [ ] 1,198 基站全量物化时画布仍可交互（有聚簇或裁剪）
- [ ] 影响分析结果可在画布上高亮呈现（与 #49 impact 端点的 UI 面）

## 附：复现

```sql
-- 资源库总量
select count(*) from resources;                       -- 1,991
-- 工作台实际物化
select count(*) from virtual_devices;                 -- 30
select count(distinct resource_type) from resources r
  join virtual_devices vd on vd.resource_id = r.id;   -- 1
```

# 附录：完整施工规格（让演示呈现为完整平台）

> 本节回答「怎么做」与「做完长什么样」。目标：**演示时呈现一个贯通 7 层的完整云网平台**，
> 而非「只有 30 个设备的半成品」。

## A. 现状与目标的差距

```
现状                              目标
─────────────────────────────    ─────────────────────────────
工作台只有 device 30 台           7 层全通，1,991 条资源按层可见
画布只有 L1 一层                  可切层浏览：L0 空间 … L6 业务
接口 32 个（从链路反推）          接口来自真实 port 90 + pon_port 20
链路 16 条（光缆走廊）            物理链路 + 逻辑承载 + 业务专线三层链路
1139 基站不可见                   1,198 基站作为接入层节点可见（聚簇）
影响分析无画布呈现                根因/影响面在画布上高亮
```

## B. 物化映射表（逐类型）

依据 `/api/schema` 的 `layer` / `domain` 元数据（**单一事实源，非手工抄写**）：

| Layer | layerName | 类型（domain） | 工作台表示 | 优先级 |
| --- | --- | --- | --- | --- |
| **L0** | 空间层 | `site` `machine_room` `rack` `duct` `manhole` `pole` | **容器/锚点**（不直接上画布；用于地理定位与层次折叠） | P2 |
| **L1** | 物理层（设备） | `device` | 虚拟设备（**已有**） | — |
| | | `port` `pon_port` | **虚拟接口**（替代当前从链路反推） | **P0** |
| | | `board` `ptp_port` | 设备子槽（可选展开） | P3 |
| **L2** | 物理层（光缆） | `cable_segment` `optical_cable` | **物理链路**（已有 #49 走廊折跳） | — |
| | | `fiber` `odf` `odf_terminal` `splice_box` | 链路属性 / 中点锚点（可用于细分走廊） | P2 |
| **L3** | 传输层 | `circuit` `otn_och` `sdh_timeslot` | **逻辑链路**（承载层，与物理链路并列显示） | **P0** |
| **L4** | 接入层 | `base_station` `bbu` `rru` `olt` `onu` | **接入节点**（无线侧，需聚簇） | **P0** |
| **L5** | 逻辑层 | `ring` `igp_domain` `vpn_instance` `protection_group` `ip_pool` | **分组/保护结构**（用分组框或边着色表达） | P1 |
| **L6** | 业务层 | `customer` `service` `leased_line` | **业务节点**（端点侧） | **P0** |

### B.1 P0 的具体含义

```
port / pon_port  → 接口
  当前：32 个接口 = 16 条链路 × 2（从链路反推，与真实端口无关）
  目标：90（port）+ 20（pon_port）= 110 个真实接口，
        按 device_ip / 设备名称归属到设备

circuit / otn_och  → 逻辑链路
  当前：circuit 只用于反推物理链路，自身不可见
  目标：作为独立的「逻辑承载层」边显示，
        与物理链路（光缆段）区分着色

base_station  → 接入节点
  1,198 个，必须聚簇（见 D 节）
  经 uplink_to（1,198 条）接入设备层

customer / service / leased_line  → 业务节点
  经 subscribed_by（14）/ provided_by（8）/ depends_on（8）
  连到传输层与设备层
```

## C. 分层可见性设计

### C.1 图层开关（画布工具带新增）

```
[L0 空间] [L1 设备] [L2 光缆] [L3 传输] [L4 接入] [L5 逻辑] [L6 业务]
   默认关闭   ✅默认开   ✅默认开   ✅默认开   默认关     默认关    ✅默认开
```

**默认组合的道理**：首次打开看到「设备 + 光缆 + 传输 + 业务」四层贯通的主干，
既有层次感又不至于压垮画布；接入层（1,198 基站）与空间/逻辑层按需开。

### C.2 边的三种语义着色

```
物理链路（cable_segment / optical_cable）   实线，灰蓝
逻辑承载（circuit / otn_och）              虚线，琥珀
业务关联（subscribed_by / provided_by）     点线，绿
接入上联（uplink_to）                      细实线，浅灰
```

### C.3 与 #49 的关系

#49 已实现「物理层优先的链路物化」——本节是在其之上**增加逻辑层边**，
而非替换。两者共存，由图层开关控制显隐。

## D. 规模保护（关键，否则画布会被压垮）

### D.1 各层节点量级

```
L0 空间     237（site 83 + machine_room 83 + rack 15 + duct 7 + manhole 14 + pole 7）
L1 设备     140（device 30 + port 90 + pon_port 20）
L2 光缆     156（cable_segment 23 + optical_cable 7 + fiber 56 + odf 15 + odf_terminal 120 + splice_box 46）
L3 传输      50（circuit 32 + otn_och 14 + sdh_timeslot 4）
L4 接入   1,239（base_station 1198 + bbu 5 + rru 5 + olt 5 + onu 10 + pon_port 20）
L5 逻辑      27（ring 2 + igp_domain 2 + vpn_instance 3 + protection_group 4 + ip_pool 5 + …）
L6 业务      26（customer 12 + service 8 + leased_line 6）
─────────────────────────────────────────
全量        1,875 节点（不含 L0/L2 的细节类型）
```

### D.2 强制要求

| 场景 | 要求 |
| --- | --- |
| 节点 > 200 | 自动启用聚簇（按地理或拓扑邻接） |
| 节点 > 1,000 | 视口裁剪：只渲染视口内 + 缓冲区的节点 |
| 默认视图 | **不加载 L4 接入层全量**（1,198 个），以聚合节点表示 |
| 布局计算 | 1,000+ 节点时禁用 force/cose 布局（O(n²)），改网格/层级 |

`GeoCanvas` 已有聚簇实现（屏幕碰撞 → 计数簇 + 点击展开），
**`TopologyCanvas` 需要补齐同等机制**。

### D.3 性能基线（纳入回归）

```
节点 ≤ 200        交互帧率 ≥ 30fps
节点 ≤ 1,000      首次渲染 < 2s
节点 ≤ 2,000      首次渲染 < 5s，且可交互
图层切换          不重新加载已加载数据（缓存）
```

## E. 演示动线（做完之后「看起来是完整平台」）

### E.1 三层递进的展示

```
① 概览页
   1,991 资源 / 32 类 / 7 层 · 质量评分 · 4 条告警
   → 传达「这是一个国家级规模的资源库」

② 拓扑工作台（默认视图）
   设备 + 光缆 + 传输 + 业务 四层贯通
   → 传达「这是有层次的真实网络」

③ 点开「接入层」图层
   1,198 基站聚簇显示，点击展开
   → 传达「这是覆盖全省的完整网络」
```

### E.2 故障故事闭环（用户的原始目标）

```
步骤 1  在画布上选中一条光缆段（OC-HDQ 哈大齐）
步骤 2  右键 → 「影响分析」
步骤 3  画布高亮：
          受影响面（向上）：电路 → 波道 → 业务 → 客户      （琥珀/绿）
          根因候选（向下）：该光缆段本身                    （红）
步骤 4  侧栏显示：#49 的 impact 结果（candidates + impacted 列表）
步骤 5  结论：「哈大齐光缆中断，影响 4 条电路 / 4 个客户 / 3 条专线」
        → 这正是「从表象找到真实故障来源」
```

**当前这一步做不了**——因为业务层与客户层根本不在画布上。
这是 #51 最核心的价值：**让影响分析有画布可呈现**。

## F. 验收清单（可直接勾选）

### F.1 物化覆盖

- [ ] `port` / `pon_port` 物化为接口（≥ 100 个），且归属正确设备
- [ ] `base_station` 物化为接入节点，经 `uplink_to` 连到设备
- [ ] `customer` / `service` / `leased_line` 物化为业务节点，经关系连到传输层
- [ ] `circuit` / `otn_och` 作为逻辑链路边可见（与物理链路区分）
- [ ] 物化输入类型 ≥ 8（当前 1）

### F.2 分层可见性

- [ ] 画布工具带提供 7 层开关
- [ ] 默认开启：L1 设备 / L2 光缆 / L3 传输 / L6 业务
- [ ] 三种边的语义着色区分（物理/逻辑/业务）
- [ ] 图层切换不重新加载数据（缓存）

### F.3 规模保护

- [ ] 节点 > 200 自动聚簇
- [ ] L4 接入层默认聚合显示（非 1,198 个独立节点）
- [ ] 1,000+ 节点时禁用 O(n²) 布局
- [ ] 性能基线纳入回归测试

### F.4 演示闭环

- [ ] 画布内可发起影响分析并高亮结果
- [ ] 故障故事可走通：选光缆 → 影响分析 → 看到业务层波及
- [ ] 全流程 ≤ 5 步，无需离开画布

## G. 实施顺序建议

```
第 1 步  接口物化（port/pon_port）          ← 最小改动，立即可见
第 2 步  逻辑链路边（circuit/otn_och）      ← 让 L3 层出现
第 3 步  业务层节点（customer/service/leased_line）
         + 影响分析画布高亮                  ← 打通用户目标闭环
第 4 步  接入层（base_station）+ 聚簇        ← 需要规模保护配套
第 5 步  分层开关 + 边着色                   ← 呈现层打磨
第 6 步  空间层/逻辑层（按需）
```

**第 1-3 步做完，平台就已经「看起来完整」了**——四层贯通 + 故障闭环。
第 4 步是画龙点睛（全省覆盖感），但必须与聚簇同时做。
