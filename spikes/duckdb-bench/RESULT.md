# DuckDB vs SQLite 分析型基准 — 费用风险分析技术验证（issue #59）

- 数据：15,000 站址 × 60 个月（2020-2024），总计 2,373,307 行
- 主表 electricity_fees：909,088 行 × 48 列（宽表）
- 风险信号注入：退租后计费 / 跨批次重复 / 合同漂移 / 环比跳变 / 零资源计费
- 加载耗时：SQLite 9.3s（Python executemany）｜DuckDB 4.7s（含 Parquet 导出）
- 体积：SQLite 393.1MB｜DuckDB 130.8MB｜Parquet 103.0MB（60 文件）

- 双引擎结果一致性抽查：2/2 项计数完全一致（Q1 退租站仍在计费、Q6 零资源季度仍计费 等）
## 附：Q4 双引擎计数差异（非缺陷，重要发现）

SQLite jump_rows=103,041 / DuckDB jump_rows=103,113（差 0.07%，jump_total 同幅度）。根因：注入的 9,088 组重复站月行（跨批次重复结算候选）使 LAG 窗口在并列行上的顺序无定义。含义：重复结算行不仅自身是风险线索，还会使窗口类分析非确定——支持「重复行在标准化阶段显式处理（以批次血缘共存，不静默合并）」的设计决策（issue #60）。

## go-duckdb (CGO) 集成验证

- `go-duckdb/v2 v2.4.3`：预编译平台绑定（`duckdb-go-bindings/linux-amd64`），**无需源码编译 DuckDB**——构建 17s、静态二进制 68MB
- 只读打开 bench.duckdb：COUNT 909,088 行（0.001s）与 Python 侧一致
- Q1 退租站仍在计费：44,021 行 / ¥31,773,722.56（0.018s）——风险信号与注入规模吻合
- 交叉编译注意：绑定按平台分包（darwin/windows/arm 齐备），Docker 部署无额外负担；CGO_ENABLED=1 + gcc 必需
