# DuckDB 分析层技术验证（spike）

对应 issue #59（跟踪 issue #58 阶段 0）。验证「费用风险分析引入 DuckDB 分析层、SQLite 留作状态层」的架构决策。

## 结论（2026-10-18 实测，2 核 / 4GB）

2.37M 行（1.5 万站址 × 60 个月 × 多费用类型、主表 48 列）、六类风险场景即席查询、双引擎零二级索引、SQL 逐字一致：

| 维度 | SQLite | DuckDB |
| --- | --- | --- |
| 六查询延迟 | 0.12-1.08s | 0.006-0.29s（×2.5-×53） |
| 512MB 页缓存敏感性 | 无助益（0.63 vs 0.74s，CPU 瓶颈） | — |
| 4 线程并发读（各 2 次 Q2） | 4.0s 墙钟，无锁死 | 2.54s 墙钟 |
| 文件体积 | 393MB | 131MB（Parquet 103MB / 60 文件） |
| 加载 | 9.3s（Python executemany） | 4.7s（含 Parquet 导出） |

- 地市级规模 SQLite 单查询尚可（<1.1s）；**省级规模（×10-20 行数）SQLite 线性劣化到 5-20s+/查询，DuckDB 大部分保持亚秒**——AI 分析循环（查询→看结果→再查询 ×50 次）的体验差距是数量级的。
- SQLite 并发读确实不锁死（WAL 验证过）——用户担心的“抗不抗住”在并发维度成立，瓶颈在单查询延迟（行存 + 单核 + 即席无索引）。
- Parquet 分区裁剪 ×2.4（60 文件 → year=2024 读 12 文件）；快照层→分析层零拷贝查询路径成立。
- go-duckdb (CGO) 最小程序构建 + 跑通 Q1（见 go-duckdb-minimal/）。
- 意外发现：**重复结算行（9088 组重复站月）使窗口函数（LAG）结果非确定**——双引擎 jump_rows 差 0.07%。支持「重复行在标准化阶段显式处理」：不静默合并、不静默丢弃、以批次血缘共存。

## 文件

- `bench.py` — 基准脚本（数据生成 → 双引擎加载 → 六查询 + 微基准 + 并发 + Parquet 裁剪），`python3 bench.py` 一键复跑，确定性种子
- `data/result.json` — 原始计时数据（gitignored）
- `RESULT.md` — 机器生成的结果表
- `go-duckdb-minimal/` — CGO 集成最小验证（独立 go module，不影响主模块）

## 边界声明

- 加载耗时是 Python 中介的（生产 Go 路径两边都会更快），仅作方向参考；查询延迟是主要裁决指标
- 本 spike 是独立模块/目录，未触碰主 go.mod 与 CI 门禁；数据全部合成
